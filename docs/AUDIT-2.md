That pass was a read-only code review; this one adds external research — official
docs for FastAPI/SQLAlchemy/Celery/Next.js/instagrapi, OWASP guidance, and a
handful of comparable open-source projects — via four parallel agents (backend,
frontend, security, scraping-domain). Findings below are deduplicated and
re-triaged against HotLead's actual threat model (self-hosted, single/few

agent claims — see file:line on every entry.

## 🔴 Critical

| # | Finding | Where | Impact |
|---|---------|-------|--------|
| C1 | **`proxy_url` is optional end-to-end.** Model, schema, and `add_account.py` all allow an account with no proxy — it just prints a warning and proceeds. | `models/account.py:26`, `schemas/account.py`, `scripts/add_account.py:73-76` | Defeats the entire point of an account *pool*: two "different" accounts with no proxy both egress from the same Coolify host IP. Instagram's abuse detection weighs IP reputation heavily — this reads as one IP running multiple sessions, a textbook multi-accounting signal that can cascade a ban across the whole pool instead of isolating it to one account. The 180/hr per-account cap (H2, already fixed) is meaningless against IP-level detection if N proxy-less accounts share a host. |
| C2 | **`Account.session_json` stored unencrypted in Postgres.** | `models/account.py:23` (`Text`, no encryption) | A session JSON is a live, working Instagram credential — it's what lets instagrapi skip `login()` entirely. The original audit verified *passwords* are never stored, but never checked whether the stored session artifact itself is protected. A DB dump, backup leak, or future SQLi hands over working sessions for every pooled account — same blast radius as leaking passwords. `add_account.py:127-128` also writes a plaintext `{username}.session.json` to local disk as a fallback when no API key is configured (gitignored, so it won't land in the repo, but still unencrypted at rest). |

## 🟠 High

| # | Finding | Where | Impact |
|---|---------|-------|--------|
| H1 | **No rate limiting on the API itself.** `require_api_key` is a pure `compare_digest` check with no attempt-tracking or lockout; nothing throttles `POST /jobs` or `POST /accounts`. | `core/security.py:11`, `api/v1/jobs.py:70`, `main.py` | A leaked key, a scripting mistake, or a compromised frontend can flood job creation, exhausting the account pool and mass-triggering cooldowns/challenges across every account at once — worse here than generic API abuse, since it directly drives the anti-ban system into a bad state. |
| H2 | **`FeedbackRequired` (Instagram action block) isn't caught anywhere.** Only `ChallengeRequired`/`LoginRequired`/`RateLimitError`/`PleaseWaitFewMinutes` are imported/handled. | `scraper/client.py:13-19` | instagrapi treats `FeedbackRequired` as a sibling exception, not a variant — it signals IG has *already* flagged the account for spammy behavior, more serious than a rate limit. It currently falls into the generic `except Exception` in `tasks.py`, which errors the job but leaves the account `status=active` — the very next checkout hands the same flagged account right back out, accelerating it toward a full ban. |
| H3 | **No escalation to `banned`.** `AccountStatus.banned` exists but is never assigned anywhere (verified: zero hits). | `models/account.py:14` | An account that keeps triggering `ChallengeRequired` cycles `cooldown → active → cooldown` forever once the H1-fix reactivation logic runs (see [AUDIT.md](AUDIT.md)). Nothing tracks a consecutive-challenge streak to trip a permanent freeze, so a clearly-compromised account keeps getting reused indefinitely. |
| H4 | **Account checkout has a real TOCTOU race** (already flagged as M5 in the first audit — this pass adds a concrete fix). SELECT-then-later-UPDATE isn't atomic, and `last_used_at` is only written at job completion, so concurrent workers can grab the same "least recently used" account for a job's entire duration. | `workers/_sync_helpers.py:207-231` | Two jobs hammer one account in parallel while others sit idle, skewing the rate limiting the whole pool design depends on. **Concrete fix:** `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *` — the standard Postgres job-queue claim pattern — plus a `leased_until` TTL column so a crashed worker's account self-frees instead of sticking. |
| H5 | **Extraction regexes miss common obfuscation and are Brazil-only.** `_EMAIL_RE` requires a literal `@`; `_PHONE_RE` only matches BR formats. | `scraper/extractor.py:5-8` | Users who deliberately want contact but dodge scrapers commonly write `name [at] domain [dot] com` or emoji-separated digits — well-documented evasion, not an edge case. Since contact extraction *is* the product's value, this systematically misses exactly the profiles most likely to have intentionally-placed contact info, and silently fails on any non-Brazilian phone number despite no stated Brazil-only scope. |
| H6 | **`lazy="dynamic"` on `Job.prospects` is incompatible with async SQLAlchemy 2.0** — not currently hit only because every route uses an explicit `select()` instead of touching `job.prospects`. | `models/job.py:51-53` | SQLAlchemy's own docs mark dynamic relationships as legacy/asyncio-incompatible; touching it raises `MissingGreenlet` at runtime, not at review time. One future call site that "cleans up" by using the relationship directly breaks in production with a confusing error. Cheap fix: `lazy="raise"` (fails loud immediately) or drop the attribute — it's unused. |
| H7 | **`Base.metadata.create_all` runs on every startup alongside a maintained Alembic chain.** | `main.py:24-25` | Standard guidance is Alembic-only in production. `create_all` only adds *missing* tables and never alters existing ones, so it's silently inert today — but it splits schema authority: a fresh environment's tables come from whatever the current models say, not from replaying the audited migration history (001→003), so a migration bug could go undetected until it's the only path taken. |
| H8 | **Celery/SQLAlchemy fork-safety is accidental.** The sync engine (`_sync_helpers.py:24-30`) only avoids Celery's classic prefork connection-sharing bug because `tasks.py` imports it *inside* the task function, deferring engine creation until after fork — there's no `worker_process_init` handler doing this deliberately. | `workers/_sync_helpers.py:24-30`, `workers/tasks.py:23` | A future refactor that hoists that import to module level for linting/typing "cleanliness" silently reintroduces shared-connection corruption (`SSL connection has been closed unexpectedly`), with nothing to catch it. Worth an explicit `worker_process_init` → `engine.dispose()` hook so it's robust by design, not by import order. |

## 🟡 Medium

| # | Finding | Where | Impact |
|---|---------|-------|--------|
| M1 | **API key lives in `localStorage`, no CSP header.** | `frontend/lib/auth.ts:5,9`, `frontend/lib/api.ts:35` | Standard SPA-token guidance (OWASP) is to avoid JS-readable storage for bearer credentials. Downgraded from the researching agent's "Critical" — there's currently no XSS vector in the app (no `dangerouslySetInnerHTML`, no user-generated content rendered), so this is a defense-in-depth gap, not an active hole. Worth a CSP header (cheap) regardless; the full BFF/httpOnly-cookie migration is a bigger lift better scheduled deliberately, not as a quick fix. |
| M2 | **Proxy credentials can leak into `Job.error_message`.** `proxy_url` may embed `user:pass@host`; a connection failure's exception text commonly includes it, and `tasks.py:129` stores `str(exc)[:500]` verbatim, returned via `GET /jobs/{id}`. | `scraper/client.py:56-57`, `workers/tasks.py:129`, `schemas/job.py` | Scrub credentials from `proxy_url` before any exception path can surface it, or regex-strip `://[^/]*@` before persisting `error_message`. |
| M3 | **Redis has no AUTH.** Network-isolated today (`internal` bridge only), so not remotely exploitable — but it's both the Celery broker *and* the anti-ban rate-limit counter store. | `.env.example:8`, `core/redis.py` | Anything that lands on that docker network (a compromised container, or a future service accidentally joined to `internal`) gets unauthenticated read/write — including flushing the rate-limit counters that enforce the 180/hr cap. Cheap to add `requirepass` given the isolation is otherwise correct. |
| M4 | **No `banned`/`FeedbackRequired` handling means the 200/hr default is only meaningful once C1 (proxy) is fixed.** Community consensus for a simulated-app scraper puts sustainable throughput around 1-2 req/sec per *isolated* session — 180/hr effective is conservative by that measure, but IG's limiting is largely per-IP, and this cap is scoped per-account. | `core/config.py:35-42` | Not a bug in the number itself — flagging the dependency so it isn't fixed in isolation and declared "safe." |
| M5 | **No `set_country()`/`set_locale()` geo-matching to the account's proxy.** Device UUID/session persistence itself is correct (matches instagrapi's documented save/load pattern). | `scraper/client.py` (zero hits on `set_country`/`set_locale`) | If a proxy's geography doesn't match an account's normal locale, nothing detects or corrects the mismatch — compounds with C1. |
| M6 | **No jitter on Celery retries** — fixed `countdown=120`/`300`. | `workers/tasks.py:112,117` | If Instagram broadly rate-limits the pool at once, every in-flight job retries in lockstep at the same instant, hammering the same cooling-down accounts together. Celery's own docs recommend `retry_backoff` + `retry_jitter=True` for exactly this. |
| M7 | **No `task_time_limit`/`task_soft_time_limit`; no client-side request timeout.** With `worker_prefetch_multiplier=1`, one wedged network call (dead proxy socket) parks a worker forever with no operator signal. | `workers/tasks.py`, `scraper/client.py` | Add a soft/hard Celery time limit per task. |
| M8 | **Secrets typed as plain `str`, not `SecretStr`.** | `core/config.py:17,24,25` | pydantic-settings' own recommendation — masks values in `repr()`/tracebacks/accidental logging. Cheap, real blast-radius reduction. |
| M9 | **Structured logging (`structlog`) is configured but used in 2 lines total**; every other module (`client.py`, `_sync_helpers.py`, `tasks.py`) uses stdlib `logging` with f-strings, baking `job_id`/`account_id` into unparseable message text. | `main.py` vs. everywhere else | No correlation-id middleware either. Can't filter "all logs for job X" without regex. Worth finishing the adoption now that there's meaningfully more log-worthy state (cursors, rate hooks) than when this was first set up. |
| M10 | **No indexes on the columns actual queries sort/filter by.** `jobs`/`accounts` list endpoints both `ORDER BY created_at DESC` with no index on `created_at`; prospect export sorts by `followers DESC` with none there either. | `api/v1/jobs.py:100`, `api/v1/accounts.py:48`, `api/v1/prospects.py:70` | Low urgency at current single-tenant scale; textbook gap to close before it matters. |
| M11 | **Missing baseline security headers on the API responses** (HSTS, `X-Content-Type-Options`) and no `TrustedHostMiddleware`. Frontend already sets these via Next config; backend doesn't. | `main.py` | TLS terminates at Cloudflare, which doesn't add HSTS without an explicit toggle — no layer in the chain currently guarantees it end-to-end. |
| M12 | **No dependency vulnerability scanning in CI.** Dependabot opens version-bump PRs weekly, but nothing runs `pip-audit`/`npm audit`/an OSV scan on every push. `mypy` is referenced in tooling but not actually run in CI. | `.github/workflows/ci.yml` | Add a `pip-audit` step and an `npm audit --audit-level=high` (or GitHub's Dependency Review Action). |

## 🟢 Low

- **L1** `account_pool.py` (confirmed dead/unused, per [AUDIT.md](AUDIT.md) L5) doesn't wire the H2-fix per-request rate hook — already known via its own docstring; noted only so it isn't mistaken for a second active enforcement path. `scraper/account_pool.py`.
- **L2** Test investment is lopsided: `test_account_pool.py` thoroughly covers the *unused* async pool twin while the live sync path gets comparatively thin coverage. Layers on top of the existing L5 duplication finding.
- **L3** `allow_credentials=True` in CORS buys nothing (auth is a header, not cookies) and only widens blast radius if `cors_origins` is ever mis-set. `main.py:42`.
- **L4** No minimum-entropy startup check on `API_KEY`/`SECRET_KEY` — `.env.example` documents `openssl rand -hex 32` but nothing enforces it. `core/config.py:24-25`.
- **L5** Frontend: no `error.tsx`/`loading.tsx`/`not-found.tsx` anywhere in the route tree — App Router's own convention for this, currently hand-rolled per-page and inconsistently. Blocked in part by the 100%-client-component structure (see below).
- **L6** Frontend: every route is a Client Component (`"use client"` in all of `app/**/page.tsx` except `layout.tsx`) — a direct consequence of storing auth in `localStorage` (M1), since no Server Component can read it. Fixing M1 unblocks streaming server-fetched data instead of the current hydrate-then-fetch waterfall.
- **L7** Frontend: icon-only buttons (logout, delete, pagination) and progress bars lack `aria-label`/`role="progressbar"` — WCAG 4.1.2 gap across `app/page.tsx`, `app/jobs/[id]/page.tsx`, `app/accounts/page.tsx`, `app/jobs/[id]/prospects/page.tsx`.
- **L8** Frontend: `AuthGuard` is a `useEffect` + `localStorage` check — cosmetic, trivially bypassable, no real request-time authorization (the real gate is the backend's key check). No `middleware.ts`. Also blocked on M1's fix to become a real server-side gate.
- **L9** Frontend: `tsconfig.json` is `strict: true` but lacks `noUncheckedIndexedAccess` — the hand-duplicated `STATUS_COLORS`/`STATUS_CONFIG` maps are indexed by backend-sourced status strings with no compiler check that every value is covered.
- **L10** Frontend: React 19's `useActionState` is unused; login/new-job/pause/resume/delete each hand-roll the same loading/error `useState` shape it would collapse into one hook. Blocked on M1 (Server Actions can't read `localStorage`).

## Suggested order of work

1. **C1** (require a proxy per account) — the single highest-leverage fix for the product's actual purpose; everything else in the anti-ban chain is downstream of this.
2. **C2** (encrypt `session_json` at rest) — Fernet + a new env var, decrypt only inside `IGClient.__init__`.
3. **H2 + H3** (catch `FeedbackRequired`, add a `banned` escalation path) — natural pair, both about retiring compromised accounts instead of reusing them.
4. **H4** (atomic account claim via `FOR UPDATE SKIP LOCKED`) — closes the already-known M5 race with a concrete, standard pattern.
5. **H1** (basic rate limiting via `slowapi` or similar on `POST /jobs`/`/accounts`) — cheap, closes a real pool-exhaustion vector.
6. **H5** (extraction regex improvements) — direct product-value fix, independent of everything else above.
7. The rest (H6-H8, M1-M12, L1-L10) as capacity allows — none are urgent in isolation; H6/H7/H8 are "won't bite until someone refactors nearby" landmines worth documenting even if not fixed immediately.
